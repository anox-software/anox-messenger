# anoX V1 — Key & Session Architecture

**Status:** CURRENT  
**Architecture Baseline:** RAW1.60–RAW1.75 consolidated  
**Last synchronized:** 2026-08-19

---

## 1. E2EE Library

- **vodozemac 0.10.0** provides the Olm / Double Ratchet implementation.
- The actual vodozemac API is the source of truth for session init, pre-key messages, and one-time key handling.

## 2. E2EE Identity

- A Curve25519/Ed25519 account is created in Rust on first run.
- The `Identity` object lives in Rust and is accessed from Kotlin only through opaque `jlong` handles.
- Public keys are exportable (`curve25519_public_key`, `ed25519_public_key`).
- Private E2EE state is never exposed across the JNI boundary.

## 3. One-Time Keys

- One-time keys are generated by the local identity.
- `unpublished_one_time_keys` are used for PreKey session establishment.
- After use the private key is consumed by `create_inbound_session`.
- Terminology maps to actual vodozemac APIs, not invented Signal hierarchy.

## 4. Session Establishment

- **Outbound:** `create_outbound_session(their_curve25519_identity_key, their_one_time_key)` produces an Olm `Session`.
- **Inbound:** `create_inbound_session(their_identity_key, pre_key_message)` consumes the one-time key and returns the `Session` plus decrypted PreKey plaintext.
- First encrypted message is a PreKey (`message_type == 0`).

## 5. Local State Protection

- Android Keystore holds a non-extractable AES-256-GCM wrapping/master key.
- A separate random 32-byte state key is generated with `SecureRandom`.
- The state key is wrapped by the Keystore key and stored in app-private storage.
- Identity/session pickles are encrypted in Rust with AES-256-GCM using the state key.
- Format: `[12-byte nonce][ciphertext + 16-byte GCM tag]`.
- `allowBackup="false"` to prevent cloud restoration.

## 6. Key Separation

E2EE identity, Olm session state, local state key, device-auth key, and access tokens remain distinct. No single master key is used for all of them.

## 7. Trust / Verification

- Trust states: `UNKNOWN`, `VERIFIED`, `KEY_CHANGED`.
- Verification uses established SAS/QR semantics; no custom safety-number algorithm.
